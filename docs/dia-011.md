# Dia 011 — Estratégia de execução: tags, agendamento e relatórios

A suíte chegou a 293 testes somando as duas ferramentas. Rodar tudo a cada mudança deixou de fazer sentido: quem abre um PR quer saber em segundos se quebrou algo grave, não esperar minutos pela suíte inteira. Este dia trata **quando** cada coisa roda e **como** o resultado é comunicado.

## Suíte de fumaça (`@smoke`)

8 cenários marcados em cada ferramenta, escolhidos para responder a uma pergunta só: *a aplicação está de pé e o fluxo que gera receita funciona?*

- Login com sucesso e login com senha inválida;
- Adicionar produto ao carrinho;
- Checkout completo de ponta a ponta;
- Guarda de rota sem login (segurança);
- Ordenação do catálogo;
- Catálogo íntegro contra a massa de dados;
- Acessibilidade da tela de login;
- Compra completa em viewport de celular (Playwright).

As duas ferramentas resolvem isso de formas diferentes, o que é justamente o tipo de comparação que o projeto se propõe a mostrar:

| | Playwright | Cypress |
|---|---|---|
| Recurso | Nativo (`{ tag: "@smoke" }`) | Plugin `@cypress/grep` |
| Filtro | `--grep @smoke` | `--expose grepTags=@smoke` |
| Pula arquivos sem match | por padrão | `grepFilterSpecs=true` |

Dois detalhes que só aparecem na prática: no Cypress 15 o plugin passou a usar `--expose` em vez de `--env` (o `Cypress.env()` foi depreciado, e este projeto já roda com `allowCypressEnv: false`); e sem `grepOmitFiltered=true` os testes filtrados entram no relatório como **pendentes** — o primeiro resumo saiu com "8 aprovados, 47 pendentes", o que confunde mais do que informa.

**Ganho medido:**

| Suíte | Testes | Tempo |
|---|---:|---:|
| Cypress completa | 99 | 1m 33s |
| Cypress `@smoke` | 8 | 6s |
| Playwright completa | 194 | ~1m 20s |
| Playwright `@smoke` | 17 | 19s |

## Quando cada suíte roda

| Evento | O que roda | Por quê |
|---|---|---|
| Pull request | apenas `@smoke` | retorno rápido na revisão |
| Push na `main` | suíte completa | o que entra na branch principal é validado por inteiro |
| Diariamente (09h UTC) | suíte completa | ver abaixo |
| Manual (`workflow_dispatch`) | suíte completa | sob demanda |

O **agendamento diário** é o ponto mais importante e o menos óbvio. O alvo é um site de terceiros: ele pode mudar sem que ninguém toque neste repositório. Sem execução periódica, uma mudança no Sauce Demo só apareceria no próximo commit — que pode levar semanas. Com o cron, a suíte também funciona como **monitor do alvo**, e a quebra aparece no dia seguinte.

Esse cenário deixou de ser hipotético no dia 008, quando um teste flagrou que a descrição de um produto na fixture divergia do site.

## Relatórios uniformes nas três suítes

Cada uma das três agora publica seu resumo no GitHub Actions, no mesmo formato:

- `scripts/playwright-summary.js` (já existia);
- `scripts/cypress-summary.js` (dia 010, a partir do JSON do mochawesome);
- `scripts/api-summary.js` (novo) — lê os JSONs exportados pelo Newman e mostra requisições e asserções por collection.

Os testes de API também passaram a exportar JSON (`-r cli,json`) e a publicar o relatório como artifact, o que antes só Cypress e Playwright faziam.

## Comandos

```bash
npm run smoke        # suíte de fumaça nas duas ferramentas
npm run cy:smoke     # apenas Cypress
npm run pw:smoke     # apenas Playwright
npm run test:all     # tudo: typecheck, Cypress, Playwright, visual e API
```
