# Dia 009 — Regressão visual (Sauce Demo)

O `visual_user` existe no Sauce Demo justamente para quebrar o layout sem quebrar a funcionalidade — o tipo de defeito que passa por toda suíte funcional. Este dia ataca isso por **duas estratégias complementares**, uma em cada ferramenta.

## Estratégia 1 — Comparação de imagem (Playwright)

`toHaveScreenshot()` é nativo do Playwright, sem plugin. 8 baselines cobrindo páginas e componentes:

| Baseline | Escopo |
|---|---|
| `login.png` | página de login |
| `inventario.png` | catálogo completo |
| `detalhe-produto.png` | página de detalhe |
| `carrinho.png` | carrinho com item |
| `checkout-resumo.png` | resumo do pedido (etapa 2) |
| `menu-lateral.png` | menu lateral aberto |
| `card-produto.png` | **componente** isolado |
| `erro-login.png` | **componente**: mensagem de erro |

Decisões técnicas:

- **Projeto Playwright dedicado** (`visual`) com viewport travado em 1280×720, para o baseline não depender do tamanho da janela de quem executa;
- **Baselines por plataforma** — `snapshotPathTemplate` grava o SO no nome (`login-win32.png`). A renderização de fonte difere entre Windows e Linux, e sem isso o CI falharia contra baselines de outro SO;
- **Espera explícita de carregamento das imagens** antes de cada captura; sem isso o baseline congela um estado intermediário e o teste fica intermitente;
- **`maxDiffPixelRatio: 0.01`** — tolera antialiasing sem deixar passar regressão real (ver validação abaixo);
- **Snapshots de componente** além de página inteira: quando um card quebra, a falha aponta para o card em vez de acusar "a página mudou".

### Validação do threshold (um baseline que nunca falha é inútil)

Antes de aceitar o valor, comprovei os dois lados:

- **Não gera falso positivo**: duas execuções consecutivas contra o baseline → 8/8 verdes, zero diferença;
- **Detecta regressão real**: capturando o catálogo do `visual_user` contra o baseline do `standard_user` → **33.894 pixels diferentes (ratio 0.03)**, três vezes acima do threshold. O teste falha, como deve.

## Estratégia 2 — Asserção geométrica (Cypress e Playwright)

O Cypress não tem comparação de imagem nativa. Em vez de adicionar mais um plugin, a contrapartida aqui mede a **geometria real dos elementos** via `getBoundingClientRect()`. Essa abordagem tem vantagens próprias: roda em qualquer plataforma (não depende de renderização de fonte), não exige baseline versionado, e a falha **nomeia a causa** em vez de dizer "a imagem mudou".

Dois comandos customizados novos no Cypress: `cy.getCartAnchoring()` e `cy.getButtonColumns()`.

As três métricas foram medidas nos três usuários antes de virarem asserção:

| Métrica | standard_user | visual_user | problem_user |
|---|---|---|---|
| Distância do carrinho à direita do header | 20px | **204px** | 20px |
| Carrinho transborda o header | não | **sim** | não |
| Colunas de botões no catálogo | 2 | **3** | 2 |
| Imagens `sl-404` | 0/6 | **1/6** | 6/6 |

Cada linha vira um par de testes: o `standard_user` como **referência do comportamento correto** e o `visual_user` documentando o bug. Ter os dois lados é o que dá valor à asserção — sem a referência, o teste do bug poderia estar medindo qualquer coisa.

Contraste interessante que o dado revelou: `visual_user` quebra **uma** imagem e desloca o layout; `problem_user` quebra **todas** as imagens mas mantém o layout intacto. São defeitos de naturezas diferentes, e agora cada um tem seu teste.

## CI

Os baselines de imagem são gerados no Windows do desenvolvedor, e o runner do GitHub Actions é Ubuntu. Rodar a comparação lá falharia por diferença de plataforma, não por regressão.

A solução: no CI a suíte visual roda com **`--ignore-snapshots`** (`npm run pw:visual:ci`). As asserções de layout e a lógica dos testes são executadas e validadas; apenas a comparação de imagem é pulada. A comparação completa roda localmente com `npm run pw:visual`.

Se o projeto passar a ter Docker disponível, o caminho natural é gerar os baselines Linux no container oficial do Playwright e habilitar a comparação também no CI.

## Correção de flakiness encontrada no caminho

Ao rodar a suíte completa nos dois navegadores pela primeira vez (168 testes em paralelo), o cenário do menu lateral falhou de forma **intermitente no Firefox** — 3 falhas numa execução, 2 na seguinte, 0 na terceira. Rodado isoladamente, passava sempre.

O diagnóstico: o menu usa transição de slide da lib `react-burger-menu`, e a espera herdada era de 5 s. Com a suíte inteira concorrendo contra o site público, a montagem do menu às vezes ultrapassava esse limite. A espera passou para 15 s e o clique agora só ocorre depois de o botão estar visível, nas duas ferramentas.

Depois da correção: 30 execuções seguidas do cenário no Firefox e duas suítes completas (168/168 cada) sem nenhuma falha. Flakiness não se prova ausente, mas a causa provável foi tratada e a taxa observada caiu de ~2/execução para 0 em 3 execuções.

## Comandos

```bash
npm run pw:visual          # regressão visual completa (compara baselines)
npm run pw:visual:update   # regenera baselines após mudança intencional de layout
npm run pw:visual:ci       # roda a lógica sem comparar imagem (usado no CI)
npx cypress run --spec "cypress/e2e/dia-009-regressao-visual/*.cy.ts"
```

Nota: `npm run pw:test` agora roda explicitamente os projetos `chromium` e `firefox`, deixando o projeto `visual` fora — ele tem seu próprio comando e não deve rodar duplicado em dois navegadores.
